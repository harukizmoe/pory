## 架构

```
src/
├── main.rs          入口：命令行解析、输入处理、结果输出
├── config.rs        配置读写（~/.config/pory/config.toml）
├── cache.rs         翻译缓存（SHA-256 键、原子写、超限淘汰）
├── error.rs         统一错误类型
├── lang.rs          语言代码规范化与映射
├── progress.rs      等待动画（盲文旋转 + 微光，只在 stderr 是终端时）
├── translator.rs    核心调度：切分文本、查缓存、调用后端、拼回结果
└── backend/
    ├── mod.rs       Backend trait 定义（架构支点）
    ├── mymemory.rs  MyMemory 后端（默认）
    ├── google.rs    Google 后端
    └── ai.rs        AI 后端（OpenAI 兼容）
```

**加一个新后端 = 一个新文件 + 一行 match。** 实现 `Backend` 的三个方法
（`name` / `max_chars` / `translate`），再到 `main.rs` 的 `build_backend` 里加一行。此外什么都不用动。

这条之所以成立，是因为**策略留在上层、机制留给后端**。举个具体的例子：互翻的判定
（`resolve_swap`：什么情况下该把目标语言换成第二语言）写在 `main.rs`，判定结果作为
**请求的一个字段**（`Request::to_if_same`）传给后端 —— 三个后端各自处理它，而
`Backend` trait 一行都不用改。

## 保底机制

主后端失败时自动切换备选，翻译不中断：

```toml
backend = "ai"                      # 质量最好，但可能没 Key / 超额 / 断网
fallback = ["mymemory", "google"]   # 按顺序兜底
```

失败分两种，都会**让你看见**：

**① 后端根本建不起来**（没填 Key、名字写错）—— 在发请求之前就发生：

```
⚠ 主后端 `ai` 不可用，将改用保底后端：AI 后端需要 API Key……
你好世界
◈ auto › zh-CN · mymemory · 1 block · cache 0/1
```

**② 请求发出去但失败**（超额、断网、Key 失效）—— 运行中回退，
警告行说清发生了什么，脚注里留下完整路径（此时**整行转琥珀色**）：

```
⚠ ai 失败，回退到 mymemory：AI 后端返回 HTTP 401 Unauthorized
你好世界
◈ auto › zh-CN · ai → mymemory · 1 block · cache 1/1
```

几个刻意的设计：

- **回退必须可见。** 静默回退是不诚实的 —— 你会以为在用 AI，实际拿到的是机翻结果。
  所以有两种提示：警告行说清发生了什么，脚注显示**实际用到的后端**并转琥珀色。
- **主后端不可用时会警告并改用保底，而不是直接报错退出。** 只有**一个后端都建不出来**
  时才报错（那时报主后端的原因，最有解释力）。这条早期是「主后端不可用就报错」，
  本意是不让你以为在用 AI —— 但代价是 `backend = "ai"` 没填 Key 时，配好的 `fallback`
  形同虚设、整个工具不能用。可见性靠警告就够，不必让工具罢工。
- **运行期警告推迟到动画收尾之后才打印。** 翻译过程的警告先攒着（`Stats::warnings`），
  因为动画占着 stderr 的当前行，中途打印会被下一帧的重绘一起擦掉 —— 那等于静默。
  机制（攒警告）留在下层，**何时呈现交给上层**。
- **缓存键跟随实际成功的后端。** 若 AI 失败、MyMemory 出了结果却存在 AI 的键下，
  下次 AI 恢复时就会命中这个低质量译文 —— 那是脏数据。
- **回退后端配置错误只警告并跳过**，不阻断翻译。
- **`pory -b <名字>` 在设置时就会提醒这个后端现在能不能用** —— 免得设完了下次翻译才发现缺 Key。

## 缓存

翻译结果会被缓存，**按切分块**存储 —— 所以同一句话在不同文档里出现时也能复用。

- **位置**：`~/.cache/pory/cache.json`（Windows 在 `%LOCALAPPDATA%\pory\cache\`）
- **键**：`后端 + 模型 + 源语言 + 目标语言 + 备用目标 + 原文` 的 SHA-256
  —— 任何一项变了就自动失效，绝不会拿到错译文
- **上限**：5000 条，超出后淘汰最旧的 20%
- **格式**：普通 JSON，可以直接打开看内容
- **写盘**：原子写（临时文件 → rename）。临时文件名**带进程号**且**与目标同目录** ——
  同目录才保证 rename 是原子的，带进程号才不会让两个并发进程抢同一个临时文件
  （早期固定叫 `cache.json.tmp`，并发时后一个的 rename 会因为前一个已经把临时文件
  移走而失败）
- **`FORMAT_VERSION`**：缓存的布局或译文语义发生变化时递增，整体作废、不做迁移。
  缓存是可再生的，作废比迁移简单，也不会读到脏数据

缓存文件损坏或不存在时会**静默降级为空缓存**，绝不会因为缓存出问题就让工具不能用。

关掉缓存有两种粒度：命令行 `--no-cache` 只管**这一次**，配置里的 `cache = false`
管**以后每次都这样**。CLI 管「这一次」，配置管「以后每次都这样」，CLI 优先。

## 请求超时

所有后端都带 **30 秒请求超时**（`backend::http_client()` 是唯一出口）。这不是可选项 ——
没有它，连接一旦挂起（出口被墙、DNS 返回了不可达的地址），请求会一直等到内核 TCP 超时
（Linux 约 130 秒），看起来就是「卡住」；而且保底后端也轮不上，因为回退发生在上一个后端
**返回失败**之后。超时后会明说：

```
✗ 网络请求失败：请求超时（超过 30 秒），网络可能不通或被墙。若用 google 后端，国内通常需要代理
```

长文本会被切成多块，**每块各自计时**。

## 设计取舍

几个刻意的决定，都有理由：

1. **装饰走 stderr，译文走 stdout** —— 这样 `pory "..." > out.txt` 得到的文件里只有干净译文。
   颜色与动画再叠一条：**只在对应那条流是终端时才加**，重定向 / CI 里行为不变
2. **配置缺失不算错误** —— 工具不该因为没配置文件就不能用
3. **后端串行请求** —— 免费接口对并发敏感，同时发多个请求容易触发限流；慢一点但稳
4. **用 rustls 而非 native-tls** —— 纯 Rust 实现，交叉编译到 musl / ARM 不用折腾系统库
5. **缓存存 JSON 而非 SQLite** —— 个人使用量级下 JSON 的读写开销可忽略，
   换来零额外依赖 + 用户能直接打开看内容。条目上到十万级再换不迟
6. **缓存键用 SHA-256 而非 64 位哈希** —— 64 位哈希更快，但碰撞后会返回
   **错误的译文**。这个后果太严重，不值得省那点计算
7. **缓存故障不算失败** —— 文件损坏、读不到、写不进去，都只降级不中断。
   缓存是优化，不是必需品，绝不能因为它让翻译本身失败
8. **译文只加粗、不上色** —— 提示符本来就是彩色的，译文再用强调色就和命令行
   糊在一起；而且 pory **猜不到用户的提示符配色**，素色加粗是任何主题下都成立的做法
9. **脚注用 `◈` 起头，符号一律落在第 0 列、内容从第 2 列开始** —— 让 pory 的
   每条输出和命令行文字同列。`◈` 是「多边形套多边形」，对得上多边兽这个名字
10. **tokio 只开 `rt`，不用 `rt-multi-thread`** —— 请求是串行的，多线程没有收益；
    更糟的是多线程下 async 写 stderr 会和主线程输出交错，实测出现过 `⚠ a⚠ ai 失败…`
    这种撕裂。单线程运行时从结构上排除了这个问题
11. **能本地判断的别问服务器** —— 显式源语言等于目标语言时直接原样返回，
    省掉一次网络往返
12. **新功能一律 opt-in** —— 判断一切新特性的上位约束是「它让二进制 / 启动 /
    单次调用变慢了吗」。不配置时，代码路径与行为必须和加之前完全一致
