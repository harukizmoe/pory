# pory 术语表 · 候选池

> 状态：**内容底稿**。术语表功能尚未实现，本文件是喂给它的原料。
>
> **用法：先划掉，再加。** 每一行都要能回答「**不保护它，会发生什么？**」
> 答不上来的就删掉。**表短是优点** —— 短表才会被读、才敢改。
>
> **进表要过两层判据**：① 该不该翻（文首第一层）② 能不能进表（同形检验）。
> 第二层最易被忽略 —— 很多词「确实该保护」，但**保护本身有副作用**，同形词尤甚。
>
> 下文标 ⚠️ 的是「引擎几乎一定翻错」的高危项；标 `?` 的是「引擎可能本来就翻对」，
> 需要用你自己的语料实测后再决定留不留。
>
> **分组**：A 绝不翻译（专名，高危）· B 已定处置 · C 同形词危险区（先不放）
> · D 同形词的出路（设计备忘）· E 反例（用来校准判据）

---

## 判据（决定一行该不该存在的唯一标准）

| 理由 | 处置 | 例子 |
|---|---|---|
| **不该翻** —— 专名、品牌、协议 | 原样保留 | `Rust` `Cargo` `GitHub` |
| **会翻错** —— 有既定中文译法，但引擎自己编 | 指定译法 | `borrow checker` = 借用检查器 |

两条硬约束：

1. **多义词不进表。** 术语表是**上下文无关**的字符串替换，做不到「按语境定」。
   （对照：机器之心的编译标准里有「歧义术语按语境定」—— pory 做不到。）
   硬塞进去就会出现「这个语境对、换个语境错」，比不保护更糟。
2. **过短的常见词不进表。** 保护 `the` / `and` / `is` 会把文本变成满屏占位符，
   后端看到 `{{1}} {{2}}` 直接翻得一团糟。**这是质量问题，不是性能问题。**

## A. 绝不翻译 —— 高危（引擎几乎一定翻错）

判据：**这个词有官方中文名吗？没有 → 不翻。**

### A1. 编程语言 / 运行时

| 词 | 不保护会变成 |
|---|---|
| ⚠️ `Rust` | 生锈 |
| ⚠️ `Python` | 蟒蛇 |
| ⚠️ `Go` | 去 / 走（极常见动词，高危） |
| ⚠️ `Java` | 爪哇 |
| ⚠️ `Swift` | 迅速 / 雨燕 |
| `C` `C++` `C#` | （一般没事，但 `C#` 可能被吃掉） |
| `JavaScript` `TypeScript` | （一般没事） |
| `Kotlin` `Scala` `Haskell` `Elixir` `Zig` `Nim` | （生僻词，风险中等） |

### A2. 构建 / 包管理

| 词 | 不保护会变成 |
|---|---|
| ⚠️ `Cargo` | 货物 |
| ⚠️ `cargo` | 货物（子命令前缀，如 `cargo build`） |
| `rustup` `rustc` `clippy` `rustfmt` `rustdoc` | （生造词，风险中等） |
| ⚠️ `crates.io` | 会被拆开译 |
| ⚠️ `npm` `pip` `yarn` `pnpm` `Homebrew` | （`yarn` = 纱线，`pip` = 果核） |
| `CMake` `Makefile` `Maven` `Gradle` `MSBuild` | （风险中等） |

### A3. 库 / 框架（Rust 生态）

含真实英文单词的**风险高**，生造词风险低 —— 但生造词也可能被后端当成拼写错误改写。

| 高风险（是真词） | 生造词（风险中等） |
|---|---|
| ⚠️ `clap` —— 拍手 | `tokio` |
| ⚠️ `rayon` —— 人造丝 / 光线 | `serde` |
| ⚠️ `hyper` —— 亢奋 / 超 | `axum` |
| ⚠️ `tracing` —— 追踪 | `actix` |
| ⚠️ `tower` —— 塔 | `warp` |

### A4. 平台 / 服务 / 工具

`GitHub` `GitLab` `Docker` `Kubernetes` `PostgreSQL` `MySQL` `MariaDB` `Redis`
`Nginx` `Apache` `Vim` `Neovim` `Emacs` `VS Code` `Firefox` `Chrome`
`Linux` `Windows` `macOS` `WSL` `Ubuntu` `Arch Linux` `Debian` `Android` `iOS`

> 注意 `Windows` —— 单独出现时引擎可能译成「窗户」。`Apache` 也可能触发「阿帕奇」。

### A5. 协议 / 格式 / 缩写

`HTTP` `HTTPS` `TCP` `UDP` `DNS` `TLS` `SSH` `FTP` `SMTP`
`JSON` `YAML` `TOML` `XML` `HTML` `CSS` `CSV` `Markdown`
`UTF-8` `ASCII` `URL` `URI` `UUID` `Base64`
`API` `SDK` `CLI` `TUI` `GUI` `REPL` `ORM` `JWT` `CORS`
`CPU` `GPU` `RAM` `SSD` `HDD` `OS` `VM`

> A5 这一组**大概率引擎本来就翻对** —— 全大写缩写很少被误译。
> 建议**先不放进表**，用真实语料跑一遍，只把真的出错的加进来。
> 记住：保护本身有副作用（占位符会打断句子），不是零成本。

## B. 已定的处置

这一组和 A 不同：**不是因为引擎会翻错，而是因为你要求统一的处置。**
前提是 —— **它得先通过同形的三问检验**。

### B1. 已定

| 词 | 处置 | 依据 | 已知代价 |
|---|---|---|---|
| `trait` | **保留 `trait` 不译** | Rust 官方中文文档同样不译（其词汇表写「本地 trait」「trait 对象类型」） | **同形词** —— 非技术文本里 `a personality trait` 会被原样留下 |

⚠️ **`trait` 这条改过一次，值得记住为什么**（2026-09-20 修订）：
最初定为「特征」（依据：Rust 社区倾向的译法）。但用户指出真正的意思 ——
**它是日常英语词时才该译「特征」，作为技术名词不该翻译。**
这个区分说明 `trait` 的问题是**同形**，不是「风格译法」，因此已移出 B1 原来那栏，
按同形检验重新定了处置（取技术侧）。

> 取舍是自觉的：pory 主要服务技术文本，所以选技术侧。
> 代价是翻非技术文本时会出现「他的 `trait` 很内向」这种半英半中的句子 —— 别扭，但读得懂。

### B2. 待定

| 词 | 候选 | 说明 |
|---|---|---|
| ? `crate` | 「包」/ 保持 `crate` | Rust 官方词汇表译「包」；社区编码规范标「**一般不译**」。冲突，需定。同形词，但日常义（板条箱）罕见 → **风险低**。 |
| ? `feature` | 「特性」/「功能」 | Cargo 文档译「特性」，日常软件语境更常说「功能」。同形词，日常义高频 → **风险中**。 |

> ⚠️ 原「`trait`=特征 ⇒ `feature`=特性 **必须配对**」这条**已作废**。
> 配对的前提是「`trait` 译成中文会占用『特征』这个词」，现在 `trait` 保留英文，
> 前提不成立，`feature` 回归独立待定。

## C. 同形词危险区 —— **先不放**

这些词在**非技术英语**里也常用，保护它们会把正常句子一起改坏。判据见上文「同形检验」。

| 词 | 日常义（高频） | 技术义 | 风险 |
|---|---|---|---|
| `move` | 移动 | 所有权转移 | 高 |
| `match` | 比赛 / 火柴 | 匹配表达式 | 高 |
| `box` | 盒子 | 装箱 | 高 |
| `use` | 使用 | 引入 | 高 |
| `mod` | （形近 mode，无独立日常义） | 模块 | 中 |
| `impl` | — | 实现块 | 中 |
| `stream` | 溪流 / 流媒体 | 流 | 中 |
| `channel` | 频道 / 渠道 | 通道 | 中 |
| `future` | 未来 | Future（异步类型） | 中 |
| `cell` | 细胞 / 牢房 | Cell（内部可变容器） | 中 |

**策略：先不放。** 等真的见到误译、且确认它反复出现，再逐个决策，并接受它的误伤。
**可预测优于聪明** —— 聪明的东西出错时你猜不到为什么。

> `trait` 曾是这一组的常客，现在它**已按同形检验作出处置**（保留不译），见 B1 组。

### 为什么不用「形态规则」把它们救回来

想过一条路：靠上下文形态区分，比如「`trait` 后跟大写标识符 → 视为关键字」。**否决**：

1. 需要正则处理，违背**零新依赖**（不引 `regex`）。
2. 规则一多，行为就变得难以预料 —— 撞上「为什么这个词这次没保护」时无从解释。
3. **救不全** —— `dyn Trait`、`T: Trait`、`impl Trait for X` 形态各不相同，穷举不完。

## D. 同形词的出路（设计备忘，尚未实现）

术语表在结构上解决不了同形词 —— 它没有语境。按代价从小到大，可能的出路：

| 出路 | 做法 | 代价 |
|---|---|---|
| ① 不保护 | 交给后端猜 | 技术文本里被误译（MyMemory 大概率把 `trait` 译成「特征/特质」） |
| ② **选一边** | 如上，`trait` 选技术侧 | 另一边误伤，**已自觉接受** |
| ③ 分场景 | 多份术语表，调用时选（`--glossary rust`） | 多一个概念；**违背「表短是优点」的精神** |
| ④ **交给 AI** | AI 后端可在 prompt 里说「Rust 关键字保留，普通名词译『特征』」 | 需要 Key（目前无） |

**④ 最优雅** ——「看语境」正是 AI 的原生优势，而「上下文无关」恰好是术语表的短板。
所以同形词不该硬塞进术语表，应该留给 AI 后端的 prompt。

**③ 暂不考虑** —— 在还没有真实语料之前引入 profile 机制，是在为想象中的需求付复杂度。

## E. 反例：这些**别**放进来

用来校准判据 —— 它们看起来「专业」，但引擎本来就翻得对，进表只是噪音：

| 词 | 为什么不该进表 |
|---|---|
| `middleware` | → 中间件，引擎翻得对 |
| `thread` | → 线程，翻得对；而且它还有「线索」义，多义词 |
| `process` | → 进程，翻得对 |
| `pointer` | → 指针，翻得对 |
| `deadlock` | → 死锁，翻得对 |
| `HTTP` `API` `JSON` | 全大写缩写，引擎基本不动它们 |

**记住这个自问**：不保护 `middleware`，会发生什么？—— 什么都不会发生。
那就别放。**表短是优点。**

## 怎么用这份文件

1. **备 10~20 段真实语料** —— 你真的要翻的英文（Rust 文档、API 说明、正在读的文章）。
   这一步不能省：没有语料就只能凭印象，而印象靠不住。
2. **先翻一遍**，把「错得离谱」的地方逐条记下来。
3. **只把反复出现的**加进表（一次性误译不值得保护）。
4. 对每个候选词**过一遍「同形检验」三问**（见文首判据）——
   这一步最容易被跳过，因为它要求你**承认自己是双语使用者**：
   「这个词我自己平时会怎么用？」答不上来就别放。
5. **改完再翻一遍对比** —— 这就是回归测试，唯一能判断改动好坏的机制。

给每一行写「理由」（配置里用 TOML 注释）：
三个月后你不知道为什么有这行，手一抖删掉，就把「生锈」放回来了。
**这份理由就是这张表唯一的文档。**
理由里除了「不保护会怎样」，最好也写清**这道词属于哪一类**（专名 / 同形 / 生僻），
因为三类词的处置契约不同：专名永远保留、同形接受误伤、生僻待验证。
