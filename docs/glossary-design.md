## 要解决什么

`Rust`→「生锈」、`Cargo`→「货物」这类专有名词误译。

**后端无关** —— 在进入后端之前就处理完，`Backend` trait 不需要知道它存在。

## 做法：占位符保护与还原

翻译前把术语换成占位符，翻译后换回原词。

**插点位置（关键，顺序不能错）**：

```
protected = protect(text)          // ① 保护 —— 必须在切分之前
chunks    = split_text(protected)  // ② 切分（不变）
loop { translate_one(...) }        // ③ 缓存 + 后端（全都不动）
result    = restore(join(chunks))  // ④ 还原 —— 只在最后做一次
```

**为什么保护必须在切分之前**（两个理由，第二个是白捡的）：

1. 否则术语会被切在块边界上（`PostgreSQL` 腰斩成 `Post` + `greSQL`）而匹配不上。
2. **缓存键算的就是「保护后的文本」，所以术语表一改，键自动失效** ——
   缓存正确性是白捡的，不用额外往键里塞术语表指纹。
   （反过来先切分再保护，键仍是原始文本，改术语表就是脏数据。）

## 新增的真实复杂度（别假装没有）

- 新失效模式：**占位符泄漏**（后端把 `{{1}}` 改坏 → 译文里出现 `{{1}}`）。
  处理：还原前校验，不匹配则该块降级重发（不带保护）+ 警告。
- 匹配规则要定：建议**先只做一种**（大小写敏感 + 全词边界），
  「可预测」优于「聪明」。
- 必须**最长匹配优先**：术语表同时有 `Rust` 和 `Rust compiler` 时长词要先匹配。

## 轻量约束下必须遵守

- **零新依赖**（不引 `regex`）—— 纯标准库字符串扫描够用
- 术语表**放进已有的 config.toml**，不多读文件
- 空表**在最开头短路返回**，不配即零开销

**唯一需实测的点**：占位符形式（`{{1}}` ASCII 形式 vs Unicode 私有区字符）
哪个能被各后端原样透传。计划拿三个后端各跑一遍再定。

## 规模 vs 性能

2026-09-20 实测（Rust 1.95 release / WSL 原生，取中位数），文本固定 4000 字符：

| 术语数 | 逐条扫描全表 | **首字符分桶** | 建桶（一次性） |
|---|---|---|---|
| 100 | 0.50 ms | **0.036 ms** | 0.003 ms |
| 1000 | 5.15 ms | **0.17 ms** | 0.016 ms |
| 10000 | 63.7 ms | **1.5 ms** | 0.16 ms |
| 50000 | 346 ms | **7.9 ms** | 1.1 ms |

- **必须用首字符分桶**（`HashMap<char, Vec<(idx, &str)>>`），把 M×N 降成 N×k，
  比逐条扫描快 **30~45 倍**，且零依赖。50000 条这种极端规模也只要 7.9 ms。
- 桶内顺序继承全局的「长度降序」，所以**最长匹配优先**自动成立。

**真瓶颈不是匹配，是 config.toml 解析**（术语表寄存在里面，每次启动都付）：
1000 条 ≈ 0.4 ms、10000 条 ≈ 4.5 ms（Python tomllib 实测 4.4 / 45 ms，按 Rust 快 10 倍估）。
pory 净启动仅 1 ms，所以上万条术语是**唯一会让启动变得可感知**的因素。
→ 规模建议：**千条以内无感**；上万条需考虑懒解析或独立文件。

**比性能更该警惕的是文本膨胀**：占位符替换会改变切分块数。
`middleware`(10)→`{{5}}`(5) 变短，但 `impl`(4)→`{{12}}`(6) 变长。
整段膨胀 x%，MyMemory 的 400 字符切分块数就涨 x%，
**每多一块 = 多一次网络往返 ≈ +1000 ms** —— 比匹配开销大 3 个数量级。
→ 占位符应尽量短（Unicode 私有区单字符优于 `{{n}}`），目标让膨胀 ≤ 0。

⚠️ **把常见短词放进术语表是质量灾难**：若保护 `the` / `and` 这类词，
文本会变成满屏占位符，后端翻译质量直接崩。设计上应拒绝过短的术语（或给下限警告）。

## 内容建设

**核心判据**：每一行只能因两个理由存在 ——「不该翻」（专名）或「会翻错」（引擎会自己编）。
自问 **「不保护它，会发生什么？」** 答不上来的不进表。
反例：`middleware`→中间件，MyMemory 翻得对，进表只是噪音。
**表短是优点** —— 短表才会被读、被敢改。

**三层结构**（只有前两层要建）：

1. **绝不翻译 · 专名层** —— 手写，30~80 条，今天就能定完。
   判据「有官方中文名吗？没有 → 不翻」。语言 / 构建工具 / 库 / 平台 / 协议。
2. **会翻错的术语** —— **不能预先写**（写出来必定是猜的），只能从真实误译里长出来。
3. **全面覆盖** —— **明确放弃**。理由不是性能，是**表会变得不可维护**：
   出怪译文时定位不到是哪条干的 → 不敢删任何一行 → 只增不减地烂下去。

**建设闭环**：① 备 10~20 段**真实语料**（你真的要翻的英文）→ ② 先翻一遍，记下离谱的误译
→ ③ **只收反复出现的**（一次性误译不值得保护，保护本身有副作用）→ ④ 改完再翻一遍对比。
第 ① 步是全部的关键：**没有语料就只能靠印象，而印象靠不住**；有语料才有回归测试。

**把大库缩小的办法**：不整表导入微软术语库，而是拿**自己的语料去匹配它**，
3 万条会缩到几十条，且每条都有证据。
`.tbx` 转纯文本 + `grep -F -f 语料` 即可，**不用给 pory 加功能**。

**每行要带「理由」**（TOML 注释即可）。`"Rust" = ""` 裸格式的隐患是：
三个月后不知道为何有这行，删掉就把「生锈」放回来。
这份理由就是这张表**唯一的文档**。

**⚠️ 危险区：常见英文词兼术语** ——
`move` `match` `box` `channel` `stream` `future` `use` `mod` `impl`。
保护它们会把普通句子里的同形词也换成占位符（"move the file" 里的 move），句子直接变形。
**策略：先不放**，等见到误译且确认反复出现再逐个决策，并接受误伤。
仍是「可预测优于聪明」。

**多义词不该进表** —— 术语表是**上下文无关**的字符串替换，做不到「按语境定」。
（对照：机器之心的编译标准里「歧义术语按语境定」，这条 pory 做不到。）
进去就会出现「这个语境对、换个语境错」，比不保护更糟。

## 处置决定（2026-09-20，当日修订过一次）

- **`trait` → 保留 `trait` 不译**（修订后结论）。
  讨论中指出：「**如果是日常翻译，它应该被翻译为特征，但作为一个技术名词它不应该被翻译**」。
  这句话把问题从「译法选择」纠正成了「**同形词**」—— 即术语表看**词形**不看**词义**，
  做不到「按语境定」。既然 pory 主要服务技术文本，取技术侧（保留）。
  知悉：这个选择**与 Rust 官方中文文档一致**（其词汇表写「本地 trait」「trait 对象类型」）。
  代价：非技术文本里 `a personality trait` 会被原样留下（别扭但读得懂）。
- ⚠️ **原「`trait`=特征 ⇒ `feature`=特性 必须配对」已作废**：
  配对的前提是「`trait` 译成中文会占用『特征』」，现在 `trait` 保留英文，前提不成立。
  `feature` 回归独立待定（「特性」/「功能」）。
- **`crate` 待定**：官方文档词汇表译「包」，社区编码规范明确标注「一般不译」，两者冲突。

### 新增判据：同形检验（homograph）—— 进表前必过的第二层

第一层判据（该不该翻）只回答一半。第二层是「**能不能进表**」：

三问 —— ① 该词在**非技术英语**里常见吗？② 你要翻的文本里它更可能是哪个义？
③ 误伤代价多大（保留原样 → 日常句冒英文，别扭但读得懂；指定中文 → 与代码脱节，更麻烦）。

**三问全过才可进表**；同形是**程度问题**：`crate`（日常义「板条箱」罕见）风险低，
所以社区敢盖章「一般不译」；`trait`（日常中高频）风险高，没人敢这么处理。

**同形词的四条出路**（设计备忘，均未实现）：

1. 不保护（交给后端猜）
2. **选一边**（`trait` 采用了这条）
3. 分场景多表（`--glossary rust`）
4. **交给 AI 的 prompt**（最优雅 ——「看语境」是 AI 原生优势，
   而「上下文无关」恰是术语表短板）

③ 明确**暂不考虑** —— 没有真实语料前引入 profile 机制，是在为想象中的需求付复杂度。
