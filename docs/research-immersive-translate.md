## 一句话结论

它不是「一个翻译引擎」，而是**一个双语阅读层 + 引擎调度器**：把 20 多个第三方翻译 API 接进
来，用「原文不消失、译文紧随其后」的排版重新组织了人类的外文阅读方式。真正的护城河是**排版
决策**和**渠道覆盖**，不是翻译质量。

## 1. 它是什么

浏览器扩展起家（Chrome / Edge / Firefox / Safari），外扩到 iOS / Android App、桌面端。
官方口径：支持 **20+ 翻译引擎**、**100+ 语言互译**、覆盖 Chrome/Edge/Safari/Firefox 四大浏览器，
号称全球 **2000 万用户**（口径见第 6 节的存疑部分）。

## 3. 功能矩阵

**核心形态（首创，也是它最值钱的东西）**
- **网页双语对照**：智能识别正文区（跳过广告/导航/侧栏），原文下方垂直插入译文

**内容载体**
- PDF / ePub / HTML / TXT / Docx / Markdown / 字幕文件（ASS/SRT），双语或纯译文输出，扫描件 OCR
- **BabelDOC**：保留公式、图表、脚注、字体的 PDF 重排版翻译

**音视频**
- YouTube、Netflix、Prime Video、Bilibili 等 **100+ 平台**实时双语字幕
- 无字幕视频：AI 生成字幕再翻译
- Zoom / Google Meet / Microsoft Teams 实时会议翻译

**图像**
- 图片翻译：OCR + Inpaint 擦除原文字再回填
- 漫画翻译：日漫 / 韩漫 / 美漫「生肉」即时翻

**交互（它最讲究的部分）**
- 划词翻译、鼠标悬停 + 快捷键翻译、**输入框连按三次空格即译**（评论区/搜索框写作场景神技）

**AI 层**
- AI 专家（给模型指派行业角色）、**AI 术语库**（内置 + 自定义）、上下文感知翻译

## 4. 技术内核：哪部分是开源的

这点常被误解，值得说清楚：

- **扩展本体：闭源。** GitHub 上的 `immersive-translate/immersive-translate` 仓库 README 明确写着：
  「沉浸式翻译并非开源软件，这个仓库并不包含源代码」，只用来发 Release 和收 Issue。
- **BabelDOC：开源，AGPL-3.0。** `funstory-ai/BabelDOC`，约 8685 Star / 706 Fork（Python），
  是「保留排版的 PDF 翻译」的核心库，也是社区项目 PDFMathTranslate 的基础。
  免费额度：官方在线服务每月 **1000 页**。
- 也就是说它是 **「产品闭源 + 关键技术组件开源」** 的混合作法 —— 开源换口碑和技术正反馈，
  闭源保护商业产品。

## 5. 商业模式与定价

设计上有个很聪明的地方：**用户可以填自己的 API Key，用任意高级引擎，且完全不付费。**
所以它的会员不是「解锁功能」，而是**代付额度**——服务的是「想用 DeepL/GPT 但不想自己去买 API」的人。
这让免费版在舆论上站得住脚（「绝大多数功能免费无限用」是字面成立的）。

## 6. 数据口径打架的地方（重要）

- **用户量**：Chrome 商店实时显示 **300 万**，官网/各商店文案宣称 **2000 万**（全平台合计口径）。
  两个数都可能是真的（单渠道 vs 全平台），但差距 6 倍多，引用时必须标明口径。
- **评分**：Chrome 商店 **3.9 / 5（2999 条）**。这个数字跟官网「千万用户好评如潮」的叙事有明显张力 ——
  大量用户 + 中低分，通常意味着**用户基数里非技术用户占比高**（配置、报错、订阅问题拉低评分）。
  这是一个值得警惕的信号：**功能铺得越宽，评分越难维持**。
- **公司主体**：App Store 页版权写的是 `FUNSTORY.AI LIMITED`；工商登记层面另有「上海书同文网络科技
  有限公司」等关联主体说法；收购方公开可查的是「北京推文信息科技有限公司」（曾获 WiFi 万能钥匙/
  连尚文学领投 Pre-A、后续 A+ 轮）。**这些关系未全部交叉验证，别当成定论。**

## 7. 它做对了什么（我的判断）

1. **找到了一个「不对不对」的夹角**：别人在做「整页替换」，它在做「原文 + 译文共存」。
   这一个排版决策，就把「翻译工具」变成了「阅读工具」，顺带把"看不懂也能学外语"这个价值送出去。
2. **不拥有引擎，只拥有调度权**：翻译质量随第三方引擎免费升级而升级，自己不承担模型成本与迭代风险。
   这也是它能一边喊"免费无限"一边活下去的根因。
3. **把付费点放在「代付」而不是「解锁」上**：舆论上几乎无法被指责"割韭菜"，因为所有功能都在，
   付费只是买额度便利。这是极高明的 framing。
4. **「交互粒度」做得很细**：悬停、划词、三次空格。看起来是小功能，实际是把翻译塞进**你正在做的事**
   里，而不是让你切到另一个地方去翻译。这才是"沉浸式"三个字的真实含义。
5. **克制的创始人**：Owen 明确拒绝过做划词弹窗（后来还是做了，但控制在非模态），理由是"不抢用户的
   注意力"。这套「注意力自由」哲学是产品的隐形骨架。

## 8. 对 pory 的直接启示

> pory 是终端 CLI，跟浏览器扩展是完全不同的赛道，重叠度很低。真正值得抄的是**决策方式**，不是功能。

**能借鉴的**
- **「自有 Key 免费」的定价哲学** → pory 的 `ai` 后端本来就是用户提供 Key，天然同构。
  强化这一点在 README 里作为立场声明。

- **AI 术语库** → 这个是**最值得警惕的重合**：pory 的术语表设计（`docs/glossary-design.md`，当前 ⏸ 暂缓）
  跟它的 AI 术语库几乎是同一个产品判断。它的存在说明**需求是真的**；而它只是"上下文注入提示词"，
  pory 完全可以在终端场景做得更轻（不读额外文件、不到阈值不加载 → 正好符合 pory 的 opt-in 铁律）。

- **保留排版的 PDF/字幕翻译** → 这是终端 CLI 最难覆盖的一块，属于"不必追"的能力。pory 守住
  「把一段文字翻好」即可。

- **克制的交互** → pory 已有的「机制只产出事实，何时呈现交给上层」「译文 stdout / 装饰 stderr」
  是同一套哲学的终端版本。**这条不用改，继续坚持。**

- **反面教训**：它的 3.9 分提醒我们 —— **功能越叠越多，体验分越难守**。
  pory 的「轻量、快速」上位约束正好是对症的解药。别丢。

**不必借鉴的**
- 全平台铺开（App / 桌面 / 会议翻译）—— 与 pory 的定位冲突。
- 会员体系 —— pory 没有服务器，没有边际成本，不需要。
- 闭源主体 + 组件开源的混合模式 —— pory 是 MIT 整体开源，更干净，别把它搞复杂。

## 9. 与 pory 的定位对照

| 维度 | 沉浸式翻译 | pory |
|---|---|---|
| 形态 | 浏览器扩展 + 全平台 App | 终端 CLI |
| 核心价值 | 在原地，不打断阅读 | 在管道里，可组合可脚本化 |
| 翻译入口 | 20+ 引擎，可自带 Key | 3 后端 + 回退链，免 Key 优先 |
| 缓存 | 云端（不明显） | 本地切分块级缓存，命中 4 ms |
| 安装成本 | 装扩展 / 装 App | 一条 cargo install |
| 典型动作 | 读一篇外文网页 | `pory "$(xclip -o)"` / `cat paper.txt \| pory` |
| 商业模式 | Freemium 卖额度 | 无（MIT 开源个人项目） |

**简言之**：它服务的是「人读」，pory 服务的是「机器用 / 管道用」。这两者几乎不竞争 ——
真正的竞争关系在 Google Translate 网页版、DeepL 客户端这一侧，而不是 pory。
